======================================================================

[사용자]

이동하도록 변경해 주세요. 이동 위치 xyz는 블록 위치로 해주세요.

[응답 및 작업]

MuJoCo의 body_position("red_block")에서 실제 좌표를 읽도록 변경했습니다.

실행 결과 예:

  target: [-0.25, 0.0, 0.04]
  code: IK_SUCCESS

======================================================================

[사용자]

6. Stage 6 Harness 및 물리 grasp 개선
======================================================================

[사용자]
앞서 설명한 개선사항을 모두 반영해 주세요.

[응답 및 작업]
다음 내용을 구현했습니다.

1) 공통 Skill 계약

모든 Skill이 다음 인터페이스를 사용합니다.

  schema()
  validate_args(args)
  execute(args)

대상 Skill:

  MoveToSkill
  MoveToObjectSkill
  GraspSkill
  LiftSkill

2) Registry와 Harness

SkillRegistry가 허용된 Skill allowlist를 관리합니다. Harness는 다음 항목을 검사한
뒤에만 Skill을 실행합니다.

  - plan이 list인지
  - 최대 step 수 이내인지
  - 각 step이 정확히 skill, args 키를 갖는지
  - skill이 allowlist에 등록되었는지
  - args가 각 Skill schema에 맞는지

3) 객체 이름 기반 이동

계획에는 xyz가 들어가지 않습니다.

  {"skill": "move_to_object", "args": {"object": "red_block"}}

MoveToObjectSkill이 MuJoCo에서 red_block의 현재 위치를 읽고 내부 MoveToSkill에
xyz를 전달합니다.

4) 실제 그리퍼 및 contact

단순 평행 gripper pad와 actuator를 MuJoCo 모델에 추가했습니다. GraspSkill은
gripper를 닫고 red_block과의 실제 MuJoCo contact가 발생한 경우에만 성공합니다.
접촉이 없으면 GRASP_NO_CONTACT를 반환합니다.

5) 물리 결합

접촉이 발생한 뒤 weld constraint를 활성화하여 lift 중 블록이 그리퍼를 따라가도록
구현했습니다.

Stage 6 고정 계획:

  [
    {"skill": "move_to_object", "args": {"object": "red_block"}},
    {"skill": "grasp", "args": {"object": "red_block"}},
    {"skill": "lift", "args": {"dz": 0.05}}
  ]

8. Stage 7 핵심 코드에 대한 질문
======================================================================

[사용자]
다음 코드가 실제로 LLM에 문의하고 plan을 받아 Harness를 통해 Skill을 실행하는
실체 코드가 맞나요?

  plan = self.planner.plan(command, self.harness.registry.schemas(), before)
  try:
      execution = self.harness.run(plan)
  except (TypeError, ValueError) as error:
      ... PLAN_REJECTED ...

[응답]
맞다고 설명했습니다.

  self.planner.plan(...)
    -> Qwen에 자연어 명령, Skill schema, 현재 상태 전달
    -> 실제 HTTP 요청
    -> Qwen JSON 응답 추출

  self.harness.run(plan)
    -> plan 구조 검증
    -> Skill allowlist 검사
    -> args 검사
    -> 등록된 Skill execute(args) 호출
    -> IK와 MuJoCo 동작

try/except는 Qwen이 허용되지 않은 Skill이나 잘못된 인자를 만들었을 때 로봇이
움직이기 전에 PLAN_REJECTED로 차단하는 안전 경계입니다.

9. Stage 8: try-fail-replan-retry
======================================================================

[사용자]
Stage 8을 만들어 주세요. 마지막 Stage이며 try-fail-retry 시나리오가 목표입니다.
Harness에 복구 Skill sequence를 하드코딩하지 않고 LLM 명령에 재시도를 설정하면
LLM이 알아서 재시도 Skill sequence를 만들 수 있을까요?

[응답]
"실패하면 재시도해"라는 문장만 한 번 LLM에 보내 미래의 실패까지 포함한 sequence를
미리 만들게 하는 방식은 신뢰하기 어렵다고 설명했습니다. IK 실패나 접촉 실패는
실행 후에야 알 수 있기 때문입니다.

다음 책임 분리를 제안하고 구현했습니다.

  LLM:
    실패 원인과 최신 상태를 보고 다음 복구 Skill sequence 결정

  Harness:
    실패 감지
    LLM 재호출
    재시도 횟수 제한
    새 계획 검증
    안전 정책 강제

Stage 8 흐름:

  Qwen 최초 plan
  -> Harness 검증 및 실행
  -> Skill 실패
  -> 실패 코드, 완료된 Skill, 이전 plan, 최신 MuJoCo 상태 수집
  -> Qwen 재호출
  -> Qwen 수정 plan 생성
  -> Harness 재검증 및 재실행

복구 sequence 자체는 Harness에 하드코딩하지 않았습니다. max_retries만 Harness가
0~3 범위에서 강제합니다.

실행 명령:

  python -m stage8_retry_harness.main --max-retries 2 \
    "빨간 블록을 들어 올려 주세요. 실패하면 원인에 맞게 다시 계획하세요"

첫 grasp 실패를 의도적으로 주입하는 데모:

  python -m stage8_retry_harness.main --demo-failure --viewer --duration 10 \
    "빨간 블록을 들어 올려 주세요. 실패하면 원인에 맞게 다시 계획하세요"

10. Viewer에서 블록이 날아가지만 성공으로 종료되는 문제
======================================================================

[사용자]
Stage 8을 viewer로 테스트하니 첫 번째 시도에서 그리퍼가 블록을 쳐서 블록이
날아갔는데 재시도하지 않고 TASK_SUCCESS로 종료되었습니다. 로그에는 grasp와 lift가
성공했고 retries_used가 0으로 표시되었습니다.

[분석]
Harness가 재시도하지 않은 직접 원인은 모든 Skill이 ok=True를 반환했고 최종 성공
판정이 held_object 문자열만 검사했기 때문입니다.

블록이 날아간 원인은 비활성 weld를 활성화할 때 XML 로딩 당시의 초기 상대 자세가
사용되었기 때문입니다. 접촉 지점의 현재 상대 자세가 weld constraint에 반영되지
않아 블록이 잘못된 위치로 순간이동했습니다.

[수정]
attach_red_block()에서 weld 활성화 직전에 다음 값을 계산하도록 변경했습니다.

  relative_position = R_gripper^T * (p_block - p_gripper)
  relative_quaternion = inverse(q_gripper) * q_block

계산한 현재 상대 pose를 model.eq_data의 weld relpose에 기록한 뒤 constraint를
활성화합니다.

최종 성공 조건도 강화했습니다.

  held_object == "red_block"
  block height increase >= 0.02m
  distance(block, TCP) <= 0.05m

이 조건이 충족되지 않으면 GOAL_NOT_REACHED로 처리하고, 실패 내용과 최신 위치를
Qwen에 전달하여 재계획합니다.

수정 후 확인한 값:

  block lift: 약 0.0468m
  block-TCP distance: 약 0.0025m

Stage 7~8 자동 테스트 6개가 통과했습니다.
